# Bug Report：定位 → RCA → 修復方案 → Ticket

一個精簡的四階段流程：定位涉及服務 → 根因分析（RCA）→ 提出修復方案 → 產出標準化 ticket 文件。請依序執行所有階段，切勿跳過任何階段。

**硬性限制 (Hard gate)**：在完成 RCA 之前，**絕對不得**產出 ticket，更**不得**修改任何程式碼。

## 觸發條件 (Trigger)

使用者透過 `/br <bug描述>` 或 `/bug-report <bug描述>` 呼叫此技能。若未提供 bug 描述，請詢問使用者 bug 的具體現象。

---

## Phase 1: 定位與蒐集 (Locate & Gather)

**立場**：快速建立 bug 的全貌，不深入程式碼。

### 步驟（請依序執行）

1. **輕量定位涉及服務**
   - 檢查當前工作目錄是否存在 `topology.yaml`，或 `../system-architecture/topology.yaml`、`./system-architecture/topology.yaml`
   - 若找到，讀取並對照 bug 現象，初步判斷涉及哪些服務
   - 若找不到，直接略過，不阻塞流程
   - 向使用者展示涉及服務的判斷結果，並確認是否正確

2. **蒐集 bug 資訊**（一次只問一個問題，優先使用單選/多選題）
   - 重現步驟：如何穩定重現？
   - 預期行為 vs 實際行為
   - 環境資訊：發生時的操作情境（輸入、資料量、觸發時機）
   - 是否偶發：固定重現，還是特定條件下才發生？

3. **確認準備就緒**
   - 說明：「Phase 1 完成。bug 全貌已建立。準備進入根因分析。」
   - 繼續進行 Phase 2

### 行為準則
- 此階段**不得**閱讀程式碼或推測根因，專注於蒐集現象
- 若資訊不足，寧可多問，也不要急著猜測

---

## Phase 2: 根因分析 (RCA)

**立場**：嚴謹的偵探。透過程式碼探索找到真正的 root cause，而非表象。

### 步驟（請依序執行）

1. **探索程式碼庫**（優先於詢問使用者）
   - 進入 Phase 1 定位的服務，透過 grep / read 追蹤相關程式碼
   - 沿著資料流追蹤：輸入 → 處理 → 輸出，找出破綻發生點
   - 檢查相關的錯誤處理、邊界條件與資料格式假設

2. **確認根因**
   - 以 `file_path:line_number` 格式標記根因位置
   - 判斷是否為唯一根因，或存在多個協同因素
   - 向使用者展示 RCA 結果，確認是否與實際觀察吻合

3. **確認準備就緒**
   - 說明：「Phase 2 完成。根因已鎖定。準備提出修復方案。」
   - 繼續進行 Phase 3

### 行為準則
- 若透過程式碼探索就能解答的問題，**不得**詢問使用者
- RCA 結果必須附上具體程式碼位置，而非模糊描述

---

## Phase 3: 修復方案 (Fix Proposal)

**立場**：務實的方案提供者。提出可行的修復選項與權衡。

### 步驟（請依序執行）

1. **提出 2-3 種修復選項**
   - 每個選項附上優缺點分析
   - 將推薦方案放在最前面，並說明推薦理由
   - 標明各方案會動到的檔案清單與影響範圍

2. **取得使用者決策**
   - 詢問使用者要採用哪個方案，或決定是否交由他人處理
   - 若修復複雜到需要完整設計，提示改用 `/full-plan` 進行規劃

3. **確認準備就緒**
   - 說明：「Phase 3 完成。修復方向已定。準備產出 ticket。」
   - 繼續進行 Phase 4

### 行為準則
- ticket 僅為記錄，是否執行修復由使用者決定
- 修復本身不在此 skill 的執行範圍內

---

## Phase 4: 產出 Ticket (Deliverable)

**立場**：標準化的文件產出者。

### 步驟（請依序執行）

1. **產出 ticket 文件**
   - 取得使用者同意後，寫入 `docs/bugs/YYYY-MM-DD-<topic>-bug.md`
   - 使用下方範本，依實際資訊填寫
   - 若 `docs/bugs/` 目錄不存在，則自動建立

2. **總結**
   - 向使用者呈現 ticket 檔案路徑
   - 提醒：修復完成後，可視需要加入 `/playwright-cli` 測試工項

### Ticket 範本

```markdown
# Bug: <簡短標題>

## 摘要

## 重現步驟
1. ...
2. ...

## 預期行為
## 實際行為

## 環境資訊
- 涉及服務: <topology.yaml 定位結果>

## 根因分析 (RCA)
- 根因: ...
- 涉及檔案: path/to/file.py:line

## 修復方案
- 選項 A (推薦): ...
- 選項 B: ...

## 驗證方式
- ...

## 備註
- 修復狀態: 未修復 / 已修復 (PR: ...)
```

### 行為準則
- 寫入 `docs/bugs/` 前**必須**取得使用者同意
- 檔案內容一律使用 zh-TW

---

## 不做的事 (DRY)

- 不走需求分析（Phase 0.5）、不產出 design / tasks 文件、不更新 `PROGRESS/`
- 若 bug 修復複雜到需要完整設計 → 產出 ticket 後提示改用 `/full-plan`
