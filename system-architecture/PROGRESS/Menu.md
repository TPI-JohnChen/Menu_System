# OrientAI Menu 功能設計

**建立日期**：2026-07-29
**版本**：1.0
**適用平台**：OrientAI（單機 AI Agent，建構於 Opencode 引擎之上）
**目標使用者**：OrientAI 管理員、部門主管、使用者
**使用情境**：5人/工作室，多種 Agent 共存

## 二、RBAC 權限模型

### 2.1 角色定義

| 角色 | 跨部門資源 | 所屬部門資源 | 特殊權限 |
|:----|:----------:|:------------:|:--------|
| **系統管理員** | 全部 CUD | 全部 CUD | 可管理全部部門與使用者、修改角色定義 |
| **部門管理員** | 全部 R | 部門資源 CUD | 可自治部門（編輯部門/管理成員/調整資源權限），可指定一名代理人 |
| **部門代理人** | 全部 R | 部門資源 CUD（代理期間） | 由部門管理員指定，代理到期自動失效。非獨立角色，為 Dept Admin 的屬性 |
| **部門成員** | 全部 R | 部門資源 R | 個人任務 CUD |

### 2.2 資源 × 角色權限矩陣

| 資源 | 系統管理員 | 部門管理員 | 代理人 | 部門成員 |
|:----|:---------:|:---------:|:-----:|:-------:|
| 共用 Agent | CUD | R | R | R |
| 部門 Agent | CUD | CUD | CUD | R |
| 共用 App | CUD | R | R | R |
| 部門 App | CUD | CUD | CUD | R |
| 部門 Skill | CUD | CUD | CUD | R |
| 部門 Provider | CUD | CUD | CUD | R |
| 部門外部 Agent | CUD | CUD | CUD | R |
| 部門定時任務 | CUD | CUD | CUD | R |
| 個人定時任務 | — | — | — | CUD |
| 部門管理（建立/刪除） | CUD | ❌ | ❌ | ❌ |
| 部門管理（編輯所屬部門） | CUD | **CUD** | CUD | ❌ |
| 使用者管理（跨部門） | CUD | ❌ | ❌ | ❌ |
| 使用者管理（所屬部門） | CUD | **CUD** | CUD | ❌ |
| 指定代理人 | — | ✅ | — | ❌ |
| 資源權限總覽（跨部門修改） | CUD | ❌ | ❌ | ❌ |
| 資源權限總覽（所屬部門檢視） | CUD | R | R | ❌ |
| 角色定義修改 | CUD | ❌ | ❌ | ❌ |

### 2.3 RBAC for RBAC — 誰能管權限？

| RBAC 子功能 | 系統管理員 | 部門管理員 | 代理人 | 部門成員 |
|:-----------|:---------:|:---------:|:-----:|:-------:|
| 部門建立/刪除 | CUD | ❌ | ❌ | ❌ |
| 部門編輯（自己部門） | CUD | CUD | CUD | ❌ |
| 部門成員管理（所屬部門） | CUD | CUD | CUD | ❌ |
| 指定代理人 | — | ✅ | — | ❌ |
| 資源權限總覽 | CUD | R（自己部門） | R | ❌ |
| 角色定義修改 | CUD | ❌ | ❌ | ❌ |

**原則**：部門成員完全看不見「權限管理」選單。

## 三、部門結構設計決策

### Option A — 扁平部門（✅ 採用）

```
部門 A       部門 B       部門 C
└─ 資源       └─ 資源      └─ 資源
```

- ✅ 簡單直覺，RBAC 判斷快
- ✅ Menu / CRUD 權限設定容易
- ❌ 無法反映組織真實結構
- ❌ 沒有資源繼承（處級無法看到底下部級的彙總）

### Option B — 樹狀部門（❌ 暫不採用）

```
公司
├─ 處級 A
│   ├─ 部級 A1
│   │   ├─ 組級 A1a → 成員
│   │   └─ 組級 A1b → 成員
│   └─ 部級 A2
└─ 處級 B
    └─ 部級 B1 → 組級 B1a → 成員
```

- ✅ 符合真實組織，上層可彙總下層資源
- ✅ 權限可繼承（部級 CUD → 組級自動 R）
- ❌ **複雜度大幅增加**：角色 + 部門層級 + 資源 四維權限
- ❌ 5人工作室情境下 over-engineering

**決策**：先採用扁平部門，未來可向後相容升級為樹狀。

## 四、混合角色模型

### 固定角色（4 個，內建不可刪除）

| 角色 | 說明 |
|:----|:----|
| **系統管理員** | 內建，不可刪除，不可修改 |
| **部門管理員** | 內建，不可刪除，不可修改 |
| **部門代理人** | 非獨立角色，為部門管理員的「代理期間」屬性 |
| **部門成員** | 內建，不可刪除，不可修改 |

### 自訂角色（系統管理員可新增）

- 系統管理員在「角色定義」中自行建立
- 可自訂角色名稱，勾選各資源的 CUD/R 權限
- 可指定是否為管理角色、是否有跨部門權限
- 代理人保持為 Dept Admin 的功能，不納入自訂角色

## 五、效能監控架構

```
┌─────────┐    回報自身 TTFT/TOPS      ┌──────────────┐
│Opencode │ ←──────────────────────  │  OrientAI    │
│ 實例 A  │                           │  Dashboard   │
│         │    回報自身 TTFT/TOPS      │  效能面板    │
│Opencode │ ←──────────────────────  │              │
│ 實例 B  │                           │  比對兩者    │
└─────────┘                           │  計算消耗    │
                                      └──────────────┘
```

- **Opencode 端**：Opencode 實例回報自身的 TTFT / TOPS 數據
- **OrientAI 端**：OrientAI 也收集一次經過自身轉發後的 TTFT / TOPS 數據
- **比對**：Dashboard 同時呈現兩組數據，計算 OrientAI 造成的效能損耗

## 六、SOP 任務拆解與 Agent 工作流

### 6.1 名詞定義

| 名詞 | 說明 |
|:----|:----|
| **Human SOP** | 傳統流程文件，寫給人看的。人類閱讀時會自動補上情境、默會知識與例外判斷。同樣內容直接丟給 Agent 會變成一大段非結構化文字，AI 無法理解 200 元與 5000 元的團隊規範差異。 |
| **Skill** | 把做事方法、判斷標準與踩坑經驗打包成可重用的執行單位，包含 skill markdown、references 與 scripts 三部分。對應的是**單一任務**，不是整條工作流。 |
| **Agentic Workflow** | 由多個 Agent、Tool、Skill 與資料源組成的整條生產線，把理解、查詢、執行、回報拆成不同環節協作完成。 |

### 6.2 四步驟方法論：Human SOP → 可執行工作流

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ ① 格式    │ → │ ② 任務    │ → │ ③ 雙向    │ → │ ④ 整合    │
│   標準化   │   │   拆解    │   │   開發    │   │   執行    │
└──────────┘   └──────────┘   └──────────┘   └──────────┘
```

**Step 1 — 格式標準化**

把敘述式 SOP 改寫成 Agent 能讀懂的格式：
- **參數化**：將 mode、temperature 等情境變數抽離，同一份 SOP 支援多種情境
- **規則強度**：`Must`（硬性）/ `Should`（建議）/ `May`（可選），讓 Agent 知道哪些不能妥協
- **結構化區塊**：Parameters / Steps / Error Handling，後續可接 MCP 標準介面

**Step 2 — 任務拆解與連結**

將流程拆成多個 Pipeline Steps，每個步驟都是獨立節點：
- 具備自己的 input / output，可獨立執行、獨立 debug、甚至獨立替換
- 節點之間透過 artifact 串接（前一步 JSON → 下一步輸入）
- 某一步出錯只需修那一步，不必整條流程重寫

**Step 3 — 雙向開發與迭代**

第一版 SOP 一定有缺漏（默會知識），需要小步快跑：
- 先用自然語言讓 Agent 寫出第一版
- 實際跑一次 workflow，根據結果回頭修 SOP
- 反覆測試補進規則（如：含棉衣物不可高溫烘乾、忘記放洗衣袋…）

**Step 4 — 整合與執行環境**

SOP 需要接到真實工具才會動：
- **工具層**：資料庫、API、檔案系統、版本控制、Ticketing System
- **MCP**：AI 世界的 USB-C，讓不同 Host 用同一套標準調用外部工具
- **Human in the Loop**：高風險決策前設檢查點，避免邊界案例失控

### 6.3 可控性設計

由於 App 功能多由 Opencode + Skill 驅動，控管機制如下：

| 可控層面 | 作法 |
|:--------|:----|
| **權限控管** | App 設定共用/部門私有，Skill 部署指定部門 |
| **執行追蹤** | Skill 執行日誌 + 稽核日誌記錄每則對話往返 |
| **範圍限制** | 一切以 Opencode 實例 + 項目資料夾為 scope |
| **流程可視** | Agentic Workflow 的 Pipeline Steps 可以在 Dashboard 中視覺化監控 |
| **人工干預** | Human in the Loop 檢查點，高風險操作需確認後才執行 |

## 八、設計原則

1. **一切以 Opencode 實例 + 項目資料夾為 scope**，無全局操作
2. **Opencode 既是核心引擎，又以 Agent Server 形式被統一管理**
3. **所有資源支援部門歸屬**（共用 / 部門私有）
4. **Import / Export** 涵蓋所有可設定功能，方便資料遷移
5. **稽核日誌** 記錄所有設定變更與對話往返，確保可追溯
